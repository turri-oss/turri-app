# The window

Everything the window offers, view by view. The [README](../README.md) has the short tour.

It is written as on macOS. On Linux the window keeps its window manager's title bar, with the menus below it; Ctrl takes ⌘'s place in every shortcut; Quit is in File; Finder is the file manager; and what is macOS's alone - the Dock's badge and menu, File > Open Recent, the Window menu's list of projects - is left out: the welcome screen's recent projects and the project switcher (Ctrl+Shift+P) do their work. The preview's terminal copies and pastes with Ctrl+Shift+C and Ctrl+Shift+V, as Linux terminals do, so Ctrl+C stays the shell's.

- **Start a new project** - on the landing page (or File > New Project…, ⌘N): name a folder and choose where it goes, then which models it runs on - turri's vendors as `turri init-config` offers them - each saying whether you are signed in to the provider its models come from. Not signed in, the sheet offers to sign in to it there and then, in the sign-in sheet, before the project is made. On Amazon Bedrock, whose models - every maker pi's catalogue has there: Anthropic and OpenAI, xAI, Meta, Mistral, Qwen, DeepSeek, Amazon's Nova and the rest - where they run - a geography, or your AWS region - and the two models themselves, picked from what Bedrock serves there: turri's own pair for Anthropic's and OpenAI's, the strongest to talk to and a cheaper one to code for the others, as turri offers them. A geography other than global and us says which `AWS_REGION` to set - `ap-northeast-1` for jp, say - as pi calls Bedrock in us-east-1 unless `AWS_REGION`, or the AWS profile signed in with, names another. A turri that knows any pair (after 0.1.9) writes it and refuses a model pi's catalogue does not have; an older one writes its own, and the app puts the pair picked in their place. turri writes its `config.turri.yaml` (`initConfig`, from its host entry), the project opens on those models, and the chat starts with what turri wrote - its models; the terminal's advice on signing in is left out - ready for turri to write the first spec with you. A folder of that name with files in it already is left alone; a project given up at the models takes its empty folder with it. Then turri doctor's checks run on it, the models asked too, to see that they answer with your credentials - a word each, so it costs a little: over the project as it opens, or, when turri cannot start on the models chosen - no key for them, most often - in the new-project sheet itself, which says so and what to do, and tries again once it is seen to. The folder and its config stay either way.
- **turri** - the conversation, on the right (⌘J), as wide as you drag its edge (double-click it for the width it starts at): turri writes the spec with you and regenerates the code from it. Replies stream in, tool calls show as what they do ("Edited backend.plain"), a pulse that ends is one line in the chat - what it was, how it ended, its time and cost - coloured by its kind as in the work view, and a click opens it there, its report and spec with it, and when turri asks you something - `ask_user`, a confirm, a choice - it is docked at the foot of the chat in the message box's place, the options as buttons, and the conversation stays in view above it. While a skill of several phases runs - brood's intent, stack, testing and product - its phases are above the message box: the ones done ticked, the one it is in turning, and what that phase does. Type `/` for its commands. What turri says is Markdown, shown as it is written - lists, headings, tables, code, links (to the browser), its escapes; raw HTML in it stays text. Under the message box, on the left, how full the conversation's context is - a ring and its percent, the tokens on hover - and what the conversation has cost so far (its own model's calls; the pulses' cost is in work). The ⟳ in its header starts a new session: the conversation over, nothing of the last one carried into it, as `/new` is in the terminal - not while pulses run, as they belong to the conversation's work loop. turri knows it is in the app, not a terminal: it is given the window's views - intent, work, preview - in place of the terminal's side panel and keys, and told at each turn which view and file you have open.

- **Files** - the whole project as a tree on the left: the specs, each with its state and how much of it is built, and everything beside them - the templates they import, test scripts, resources, readmes, skills, config. Folders are listed as they are opened and again when what is in them changes, and which are open is kept for each project; what turri keeps for itself (`plain_modules`, `dist`, `.turri`) is there, quieter. Any file that is not a spec opens as text - a `.plain` template coloured by turri's grammar - to edit and save with ⌘S; what turri generates is read only, and a file that is not text opens in its own app. Right-click a row to open it elsewhere, reveal it in Finder or copy its path. Below the tree, the project's settings from `config.turri.yaml`; **debug** is a switch, off by default, that goes through the chat as `/turri-config debug true` - on, turri keeps what it writes for debugging it: every agent's whole log and session, each pulse's log (the work view's "open its log"), the test runs' outputs. Off, those go as each pulse ends, and the ledger is what is left of a pulse.
- **intent** - the `.plain` file, coloured by turri's own ***plain grammar, with each functional spec's state in the gutter beside it: a filled pink mark when its code is built, a cyan one with two ticks when its conformance tests are written and pass too - a step past built, and the spec's dot in the sidebar turns cyan when every functional spec is, a spinner while it is being built, an empty one while it is still to build - the spec said once, with how much of it is built above it. While a pulse runs, the lines it renders - what its spec change adds, or the functional spec it builds - are lit in the spec and brought into view. When turri edits the file from the chat it is taken in at once, or, over edits not yet saved, offered. Rest the pointer on a functional spec - any of its lines, or its mark - and its state pops up beside it: regenerating or conformance testing, with the pulse's stage and how long it has been at it, regenerated, regenerated and conformance tested, not regenerated yet, or new and not saved. Click a mark (a native menu) to regenerate that functional spec again or write its conformance tests - once it is built: one not built yet, new or changed, is regenerated, not again, with the others not built yet, as each is built on the ones before it, and its conformance tests wait for its code. Functional specs open collapsed to their first line, each showing how many lines it hides: click that, the line or the chevron beside its mark to open it, or Expand all to open them all - remembered for next time. The buttons go through the chat - Regenerate is `/regenerate backend.plain` - so there is one work loop, whoever asks. Regenerate (⌘R) asks how: on from where it stopped, for a module partly built - its functional specs not built yet, on top of what is, chosen first while there are any - what changed in the spec - the default, and Spec > Regenerate What Changed (⇧⌘R) without asking - chosen built functional specs again though they did not change, the whole module from scratch, or it and every module it requires from scratch - with, for any of them, how to cut the work in your words. A module with nothing built yet has no code to start over or to regenerate again, and its functional specs are each built on the ones before: it is regenerated all of it, or with its whole chain from scratch when it requires others. From scratch deletes code, so turri asks in the chat first; the marks follow at once - the module's history moving, a pulse landing or its code deleted, has them read again.
- **work** - each codebase's plan, and every pulse live: its stage, what its agent is doing and for how long, what it cost. Each pulse is headed by its summary - ten words and 70 characters at most, as turri's planner is asked to write it, and cut to that if it is longer, the whole of it on hover. What the view says can be selected and copied (⌘C); each pulse's copy button, or a right-click on it, copies it for the chat - its summary, module, number, kind and id, which turri looks it up by - or its summary or id alone. Each pulse is coloured by its kind, as the intent view marks what it does: regenerate pink, conformance cyan - the planned ones too. A pulse that ended keeps its agents' report folded - Report, or Why it failed - to open and read in full; beside it, what the pulse found the spec does not say - its spec gaps, each with what it assumed meanwhile - folded the same way. Click a pulse to see the ***plain it works on - the spec change it renders, coloured as the spec is, its lines lit and numbered among the sections around them, or the functional spec a conformance run builds - and Show in the spec lights those lines there; its agents' conversation, as chat bubbles, is the panel's other tab. Halting a pulse is turri's alone: the window has no Halt or Stop for one. When something fails that the pulse goes on past - its debugger or diagnosis, the model provider for good, a commit of its landed work - it is said once in a notice, naming the pulse, however often it fails, and marked on the pulse's card. Below this session's pulses are earlier sessions', from turri's ledger (`.turri/ledger/`), grouped by run - when it started, and how: in the app, in turri's terminal chat, a headless regenerate - the last three, and more on asking: each pulse's module, kind and number, how it ended - landed or not, who stopped it, or that its session stopped under it - how long it ran and its cost, and the same marks. They are read only. Click one for what the ledger says of it - as `turri ledger <pulse>` prints it: its rounds, test runs, verdicts, healers, what turri refused, its history - and its log, to open. Ask turri about one in the chat: it looks it up by its id.
- **preview** - the app you are building, tried in a browser or a terminal - a switch in its bar, remembered for each project (⌘3). The browser is a pane of the window: type its address - `localhost:8000`, or just `8000` - and use it as in a browser, with back, forward, reload and its developer tools. Each project starts with a fresh browser - no cookies, storage or cache of another project's, or of a session before - and nothing loaded: the address it had last is offered, to open with a click, as another project's app may answer there now. The page loads again when a pulse lands. turri sees and tries it too: the chat has browser tools on the same pane - open a page of the app, read its text and controls, read its console, click, type and send a form, take a screenshot - and the window comes to the preview while it uses them, so you watch it work. They go only to this machine's own servers (localhost), never the web, and exist only in the app. A screenshot costs more than reading the page, so only the newest is sent to the model as an image; a model that turns images down - some do that their catalogue says take them - is sent none from then on, and turri carries on in the same turn without it. The terminal is a shell in the project's folder - your login shell, with your PATH - for a CLI: type in it as in any terminal, coloured in turri's palette, and ⟳ in the bar starts a new one; it is the same shell however often you switch away and back. turri has terminal tools on it too - run a command, type into what runs or press a key (enter, ctrl-c), read what it shows - and the window comes to the terminal while it uses them. turri chooses which of the two to try something in by what it is: a CLI in the terminal, a frontend in the browser, a backend in the browser when it serves API docs to try it in (`/docs`, OpenAPI) and with curl in the terminal otherwise, anything else as it shows best; a server it starts in the terminal runs on there, for the browser to open.
- **Preview the plan** (Spec menu) - `turri glimpse`: the pulses Regenerate would run, and what the coding agent would be told, before anything starts.
- **Release** - beside Regenerate, once something of the spec is built: it asks turri in the chat to release it - the module's last commit, exported to `dist/<module>` and started on this machine - open it in the preview, in the terminal or the browser as suits it, and then say how to open it and what to test, functional spec by functional spec.
- **Check This Machine…** (Help menu) - `turri doctor`'s checks, from turri's host entry (`doctor`), run by the window's engine - so on the PATH turri runs with in the app, which is not always your shell's: Node, bash, git, the OS sandbox (Seatbelt on macOS, bubblewrap on Linux) and a model provider; with a project open, also each module's toolchains and what its testing scripts run. What wants doing comes first, each with what to do about it. **ask the models too** sends each model `config.turri.yaml` names a word, to see that it answers with your credentials - a request each, so it costs a little, and only on the click. The machine is checked when the welcome screen opens and the project when it opens, the models not asked: anything missing is said there, in amber - on the welcome screen under its buttons, in a project at the foot of the sidebar - and a click opens the checks. A turri without `doctor` (0.1.9 and before) says it cannot check.
- **Sign In to Model Providers…** (File menu) - pi's sign-ins, as `/login` runs them in turri in a terminal, in a sheet of the window's: every model provider pi knows - forty or so - searchable, the ones this project's models come from first, then those with a subscription to sign in with, then API keys. Each says whether it is connected and how: signed in, an API key saved, from an environment variable (it names it), from pi's `models.json`. Choose one: a provider with a subscription and API keys both asks which - sign in with your Claude Pro/Max, say, or use an API key. A subscription signs in in your browser, which opens on its own: the sheet shows the address too, to copy or open when it does not, waits for the browser, and offers a field for the code the browser ends on, should it not reach the app - whichever comes first wins. The page the browser ends on is turri's, with its logo and colours: signed in, or why not, in the provider's words. GitHub Copilot gives a code to type on its page: the sheet shows it, and a button copies it and opens the page. An API key is a password field; Amazon Bedrock and Google Vertex ask first how - their choices as buttons. Cancel stops a sign-in at any point. What a sign-in stores is kept in pi's `auth.json` (`~/.pi/agent/`), where the turri CLI keeps it, for every project; one stored can be signed out of, while a key from the environment or `models.json` stays - it is not the app's to remove. With a project open, the sign-in goes through its chat's own model runtime, so the conversation has the credential at once - and a chat that could not start on `harness-model` without it is put on it. The sheet opens from the welcome screen (sign in to your models…) and the doctor's sheet too; `/login` typed in the chat opens it - `/login anthropic` on that provider - rather than going to the model as words, and turri is told to point you there. When a new project's models have no credentials, the new-project sheet offers to sign in to each of their providers, and opens the project again once you have.
- A window for each project, as many open as you like, each with its own engine, work loop, chat, preview and terminal. A project opens in the window in front when it has none yet - the welcome screen - and in a window of its own otherwise; one open already comes to the front instead, never in two windows at once. ⇧⌘N opens a new window. ⇧⌘P drops a list of the open projects from the top of the window, the one you were in last first - selected, so ⇧⌘P and enter go back to it: type to filter them by name or folder, and enter, or a click, brings that project's window forward. Or go from one to another as with any Mac app: the Window menu lists them by project, ⌘` goes to the next, and the Dock lists them too.
- Native menus and shortcuts (⌘N, ⇧⌘N, ⇧⌘P, ⌘O, ⌘S, ⌘R, ⇧⌘R, ⌘1-3, ⌘J, and ⌘+ ⌘− ⌘0 to zoom the text, remembered), each acting on the window in front, recent projects - on the welcome screen too, each folder once by its full path, searched and scrolled past five - a dock badge counting the pulses running in every window, progress on each window while its pulses run, and a notification, naming the project, when one lands while its window is in the background - click it to bring that window forward.
- turri's look: turri-dark by default, turri-light or the system's as chosen (View > Appearance). Neue Montreal for the interface - where it is installed, as it is a commercial font not bundled with the app, and the system's sans otherwise - Zed Mono (Zed's Iosevka build, SIL OFL 1.1, subset to woff2 in `src/fonts/zed-mono/` with its licence) for code and the spec; rounded corners, fine lines and soft shadows. turri's pixel jellyfish, from its pixel kit (`src/pixels/`, `public/jellyfish/`): on the welcome screen and in the empty chat it grows from a polyp, sinks and grows again, then sways; small, its logo mark sits in the sidebar and the chat, and the mascot bobs there while turri works. The app's icon is its logo mark.
